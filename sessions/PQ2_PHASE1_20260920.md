pp512 = 650 t/s ≈ 107% of 608 GB/s → GEMM path saturates BW; hardware fine.
All tg headroom loss is in the decode path (shared), not the hardware.

## Optimizations tried (kernel-local)
1. SIMD 2-bit decode (T/U spread + SWAR borrow-safe sub), verified by
   exhaustive 65536-value sweep vs scalar ref. Result: 10.57 — **0% gain**.
   (First version had a cross-byte borrow bug: `x - 0x01010101` ripples.
   Fix: `((x|0x80808080) - 0x01010101) ^ 0x80808080`.)
2. VDR 1→4 (one lane per 128-elem block, 32 blocks/warp, 16 int16 words +
   32 dp4a per lane, per-chunk `sumi[4]` with per-chunk `ds[0]` scales —
   single shared d8 would be WRONG). Verified: 200-block python model vs
   scalar reference, ALL PASS. Result: 10.99 — **+4% only**.

## Conclusion (measured, not theorized)
Kernel-local ALU/load-pattern changes do NOT move tg. The bottleneck is in
the shared decode path: per-op launch/quantize overhead and one-warp-per-row
workgroup shape. Evidence: pp is at full BW; Q6_K's mmvq also caps at 49% BW
(itself 2x below its own pp efficiency); PQ2_0 kernel 4x ALU reduction = +4%.

## Next levers (in expected impact order)
1. Two-batch overlap (TBO) / graph capture to hide launch latency.
2. Fuse q8_1 quantize into the matvec (skip the separate quantize kernel).
3. Multi-row per warp (like the ncols_dst>1 variants) for better occupancy.
4. FlashInfer-style persistent decode kernel (Phase 2 idea).
